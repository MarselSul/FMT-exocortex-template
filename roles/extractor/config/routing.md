## 3. Именование файлов

**Конвенция:** `{PREFIX}.{TYPE}.{NNN}-{slug}.md`

| Компонент | Источник | Пример |
|-----------|----------|--------|
| `PREFIX` | Колонка «Префикс» из таблицы 1 | `УП` |
| `TYPE` | Код типа (ENTITY, METHOD, FM, WP, CHR, SOTA, ...) | `METHOD` |
| `NNN` | max(существующий) + 1 | `005` |
| `slug` | kebab-case из названия | `handler-per-state` |

## 4. Тест маршрутизации

Для каждого кандидата:

0. **Моя ли это запись?** → см. §6. Если кандидат в зоне другого агента — не писать, оформить как передачу
1. **Домен?** → определи Pack по таблице 1
2. **Тип знания?** → определи директорию по таблице 2
3. **MCP-проверка:** `knowledge_search("тема кандидата")` → нет ли уже в базе?
4. **Проверка bounded context:** Прочитай `00-pack-manifest.md` целевого Pack'а — попадает ли кандидат в scope?
5. **Если не попадает ни в один Pack** → предложи defer и уточни у пользователя

### Разграничение между Pack'ами
Проектное управление и прогрессивное пакетирование соприкасаются. Правило: если знание про построение, расчёт и актуализацию графика, роли участников, состав документации, стандарты — это УП. Если про состав рабочих пакетов, условия их выдачи в работу и снятие ограничений — это ПП. Пакет работ по AWP соотносится с работой детального графика (уровень 4, см. УП.ENTITY.001), но добавляет собственное требование: выдача только после снятия ограничений.

## 5. DS Routing (реализационное знание)

> Реализационное знание (вендор, стек, деплой, конфигурация) → DS-репо, **не Pack**.
> Один pipeline KE → два выхода: domain → Pack (§1-4), implementation → DS docs/ (§5).

| Признак | Куда маршрутизировать |
|---------|----------------------|
| Используется в другом проекте/контексте? **Да** | → Pack (доменное) |
| Привязано к конкретному стеку/вендору? **Да** | → DS docs/ (реализационное) |
| Описывает «что» и «почему» (архитектурный паттерн)? | → Pack |
| Описывает «как именно» (конфигурация, deployment)? | → DS docs/ |

### DS-репо по системам

| Система/направление | DS-репо | Путь к docs/ |
|---------|--------|-------------|
| Автоматизация ИСУП Холдинга (АО «НПК «Техмаш») | DS-proektnoe-upravlenie | DS-proektnoe-upravlenie/isup-automation/ |
| Проектная лига (сообщество) | DS-proektnaya-liga | DS-proektnaya-liga/ |
| Книга «Проектоград» / «Право на ошибку» | DS-proektograd | DS-proektograd/book/ |

### Директории в DS docs/

| Тип реализационного знания | Директория | Формат |
|---------------------------|-----------|--------|
| Сценарий использования | `docs/scenarios/` | Отдельный файл |
| Процесс / алгоритм | `docs/processes/` | Отдельный файл |
| Схема данных | `docs/data/` | Отдельный файл |
| Архитектурное решение (стек, интеграция) | `implementation.md` в C.IT-Platform | Секция в файле |

### Формализация DS-кандидатов

DS-кандидаты **не требуют** frontmatter с trust/epistemic_stage (в отличие от Pack). Формат:

```markdown
# {Название сценария/процесса}

## Описание
{Что делает}

## Шаги / Алгоритм
{Как работает}

## Связи
- Pack: [{ID}](path) — доменное основание
- Код: `{module/file}` — реализация
```

## 6. Разделение труда между агентами

> Разделы 1–5 отвечают на вопрос «куда попадает знание». Этот раздел — на вопрос «кто его туда несёт».
> Каждый агент начинает сессию без памяти о договорённостях. Границы поэтому должны быть записаны здесь, а не задаваться голосом в каждой новой сессии.

| Агент | Задача | Пишет в | Не пишет в |
|-------|--------|---------|-----------|
| Собеседник (Claude) | Проектирование решения, разбор спорных вопросов, сквозные темы | `DS-proektnoe-upravlenie/isup-automation/`, `DS-proektograd/`, `PD-persona/` | Pack — доменное знание собирается другими |
| КСП | Сбор и структурирование доменного знания по календарно-сетевому планированию и проектному управлению | `PACK-proektnoe-upravlenie/` | DS — реализационные решения Холдинга |
| Прогрессивное пакетирование | Доменное знание по AWP: типы пакетов, ограничения, последовательность внедрения | `PACK-progressivnoe-paketirovanie/` | DS — то же |
| МОЯ IWE | Траектория развития: цели обучения, компетенции, приоритеты | цифровой двойник, `1_declarative/` | Pack и DS |

### Правило раздвоения знания

Если знание одновременно доменное и реализационное — оно **раздваивается**, а не выбирает одну сторону:

- практика, как она существует в мире (стандарт, чужой опыт, метод) → Pack
- решение, принятое для Холдинга по этой практике → DS, со ссылкой на Pack-основание

Отработанный пример. Пятиуровневая модель вертикальной интеграции ИСУП и регламенты АО РусГидро лежат в `PACK-proektnoe-upravlenie` (УП.ENTITY.001) — это чужая практика, применимая где угодно. Решение «ИСУП АДВАНТА принимает своды, деталь живёт в модуле, граница между уровнями 3 и 4» лежит в `DS-proektnoe-upravlenie` (раздел 8.1 целевого решения) со ссылкой на ту же сущность — это наш выбор, вне Холдинга не применимый.

### Failure mode, от которого защищает раздел

Два агента пишут об одном предмете в разные файлы и по-разному; через год неясно, какой файл главный. Типичная форма: агент по доменному знанию записывает в Pack решение, принятое для Холдинга. Это нарушение УП.HD.003 (доменное ≠ реализационное) — различение, которое само должно это предотвращать, но предотвращает только если прочитано до записи, а не после.

### Оформление передачи

Если кандидат относится к зоне другого агента — не писать, а отметить передачу: кому адресовано, в какой файл предполагается, одной строкой суть. Передача записывается в `config/feedback-log.md` рядом с reject/defer (§7).

## 7. Feedback (обратная связь)

При reject/defer — записать причину в `config/feedback-log.md`.
При повторном inbox-check — прочитать feedback-log и не предлагать аналогичные кандидаты.
